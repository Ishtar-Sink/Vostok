Visão geral

O ciclo tem três skills e um subcomando. O vostok bug check valida a forma do relato (front-matter, prefixo [harness-bug], seções preenchidas, sem sobras de template) e o vostok bug link monta o link de nova issue para quem não tem gh. A skill padrão report-harness-bug monta o relato em work/bugs/ e cria a issue em harness.repository; a skill local fix-harness-bug transforma a issue numa spec e, depois da release, responde com o marcador <!-- vostok:fix -->; a skill padrão validate-harness-bug encontra a resposta, aplica os passos e comenta e fecha a issue. Toda escrita no GitHub exige autorização do usuário.

Arquitetura e componentes

  • apps/cli/src/commands/bug.rs: subcomandos check e link; o link usa codificação percentual própria e cai para só o título acima de 8000 caracteres.
  • packages/harness/templates/bug/report.md: template do relato.
  • packages/harness/config/main.yml: chaves paths.bugs e harness.repository.
  • packages/harness/skills/default/report-harness-bug/ e validate-harness-bug/: skills distribuídas.
  • vostok/skills/custom/fix-harness-bug/: skill local, não distribuída.
  • vostok/rules/project/development-methodology.md: regra 04, do mínimo de tarefas para specs vindas de issue.
  • .github/ISSUE_TEMPLATE/harness-bug.yml: formulário de issue com as seções do relato.

O que foi feito

  • TASK-01: subcomando vostok bug, template do relato e configuração, com 7 testes de integração.
  • TASK-02: skill report-harness-bug (8 regras, 8 passos), com neutralização, vostok bug check, autorização, gh issue create ou vostok bug link, e o número gravado no relato; modelo de issue do repositório.
  • TASK-03: skill validate-harness-bug (9 regras, 9 passos): listagem pelo marcador, conferência da release, reinstalação, vostok update, retomada, conferência e comentário com fechamento.
  • TASK-04: skill local fix-harness-bug em dois modos (issue para spec; resposta depois da release), a regra do mínimo de tarefas e a seção do ciclo no README.md.
  • As TASK-02 a 04 rodaram em paralelo, por subagentes; o teste de ponta a ponta usou o repositório privado Ishtar-Sink/harness-tests.

Decisões

  • gh quando houver, link preenchido sem ele, em vez de exigir o gh: o relato não pode depender de uma ferramenta instalada.
  • A correção é uma skill local, não distribuída: só este repositório corrige o harness.
  • A resposta usa um marcador HTML invisível em vez de rótulos: rótulos exigem permissão no repositório, e o marcador funciona em qualquer comentário.
  • A resposta só sai depois da release, não depois do commit: quem relatou precisa de uma versão instalável.
  • A validate-harness-bug não cita o nome do instalador, porque o teste de skills padrão recusa citações a scripts de shell; ela prefere o comando de reinstalação da resposta.

Aprendizados

  • Fora de um terminal, gh issue view --comments imprime só os comentários e sai vazio numa issue sem comentários. As skills passaram a ler a issue com --json.
  • O vostok update restaura as skills padrão a partir do binário: depois de mudar uma skill na fonte, é preciso reinstalar o binário antes do update, ou a mudança é sobrescrita e guardada em .local.
  • vostok skill create --default grava na cópia instalada; as skills padrão precisam ser movidas para packages/harness/skills/default/.
  • O GitHub não cria release num repositório vazio; o repositório de teste precisou de um primeiro commit.
  • O modo automático do agente bloqueia escritas no GitHub mesmo com autorização na conversa; foi preciso liberar gh issue nas permissões locais.

Pontos de atenção

Antes de mexer
  • A leitura sem gh pela API pública não funciona em repositórios privados e tem limite de 60 requisições por hora.
  • vostok bug check confere a forma, não o conteúdo: a neutralização depende da skill e da revisão do usuário.
  • O teste ct13 em apps/cli/tests/base.rs conta as skills padrão (17) e recusa citações a .sh nelas.
  • Ao mudar uma skill padrão, rode cargo install --path apps/cli antes do vostok update.
